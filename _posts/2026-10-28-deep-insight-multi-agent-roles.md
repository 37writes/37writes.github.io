## 어떤 문제였나

저는 혼자 개발하면서 Claude Code를 거의 모든 작업에 씁니다. 처음에는 대화 세션 하나에 모든 걸 맡겼습니다. 요청을 이해하고, 계획을 세우고, 코드를 고치고, 테스트를 돌리고, 결과를 기록하는 일까지 한 세션이 했습니다.

작업이 커지자 문제가 세 가지 생겼습니다.

1. **대화가 금방 꽉 찹니다.** 계획, 코드, 로그, 테스트 결과가 한 대화에 쌓입니다. 결국 앞부분이 요약되면서 중요한 결정이 흐려졌습니다.
2. **검증이 그때그때 달랐습니다.** 코드를 고친 세션이 스스로 "테스트 통과했습니다"라고 보고하면 그대로 믿었습니다. 만든 사람이 자기 결과를 검사하는 셈이었습니다.
3. **확인받아야 할 순간을 놓쳤습니다.** 배포나 AWS 설정 변경처럼 되돌리기 어려운 작업 전에 멈춰서 물어보는 단계가 절차로 정해져 있지 않았습니다.

이 무렵 AWS 기술 블로그에서 **Deep Insight** 시리즈를 읽었습니다. 여러 AI 에이전트가 역할을 나눠 일하는 시스템을 실제로 운영하며 얻은 교훈을 정리한 4부작입니다. 읽어 보니 제 문제와 정확히 겹쳤습니다. 그래서 이 구조를 제 개발 환경에 옮겼습니다. 이 시리즈는 그 과정을 기록한 글입니다.

첫 글에서는 Deep Insight가 어떻게 역할을 나누는지를 최대한 쉽게 설명합니다.

## Deep Insight는 무엇인가

Deep Insight는 AWS가 공개한 **멀티에이전트 데이터 분석 시스템**입니다. CSV 데이터와 "이 데이터로 매출 추이를 분석해 줘" 같은 자연어 요청을 넣으면, 여러 에이전트가 나눠서 일한 뒤 차트와 출처(인용)가 달린 보고서를 만들어 줍니다. 코드는 [GitHub(aws-samples/sample-deep-insight)](https://github.com/aws-samples/sample-deep-insight)에 오픈소스로 공개돼 있습니다.

## 역할 구조를 식당 주방에 빗대 보기

Deep Insight의 에이전트 이름은 영어 직함이라 처음에는 잘 와닿지 않습니다. 저는 **식당 주방**에 빗대어 이해했습니다. 손님(사용자)이 주문하면 요리가 나오기까지 여러 사람이 각자 맡은 일을 하는 구조입니다.

| 역할 | Deep Insight에서 하는 일 | 주방에 빗대면 | 모델(원문) |
|---|---|---|---|
| **Coordinator** | 요청을 처음 받아 분류합니다. 인사 같은 간단한 요청은 직접 답하고, 분석 요청만 Planner에게 넘깁니다 | 홀에서 주문을 받는 매니저. 물 달라는 요청은 직접 처리합니다 | Haiku |
| **Planner** | 요청을 5~10개 단계의 체크리스트 계획으로 쪼개고, 단계마다 담당을 정합니다 | 주문서를 보고 조리 순서를 짜는 주방장 | Opus (깊게 생각하기 켬) |
| **Plan Reviewer** | 사람이 계획을 보고 승인하거나 수정을 요청합니다 | "이렇게 만들어 드릴까요?" 하고 손님에게 확인하는 단계 | 사람 |
| **Supervisor** | 승인된 계획을 순서대로 실행하면서 전문 에이전트를 부릅니다 | 조리 순서표를 들고 요리사들을 지휘하는 부주방장 | Sonnet |
| **Coder** | 분석 코드를 쓰고 실행해 결과와 차트를 만듭니다 | 실제로 요리하는 요리사 | Sonnet |
| **Validator** | Coder의 계산을 원본 데이터로 **다시** 계산해 맞는지 확인합니다 | 나가기 전에 맛을 보는 검수 담당 | Sonnet |
| **Reporter** | 검증된 결과로 보고서를 씁니다 | 접시에 담아 내보내는 담당 | Sonnet |
| **Tracker** | 끝난 단계를 체크리스트에서 `[ ]` → `[x]`로 바꿉니다 | 주문표에 "완료" 도장을 찍는 사람 | Sonnet |

흐름으로 그리면 이렇습니다.

Supervisor는 현재 단계의 체크리스트 항목이 모두 `[x]`가 되기 전에는 다음으로 넘어가지 않습니다. 진행 상황을 기억에 의존하지 않고 **체크리스트 한 장**으로 판단하는 구조입니다.

## 이 구조에서 배운 5가지

Part 1이 정리한 설계 교훈을 제 말로 다시 풀면 다음과 같습니다.

### 1. 비싼 모델은 꼭 필요한 곳에만 씁니다

주문을 받는 매니저에게 주방장 급여를 줄 필요는 없습니다. Deep Insight는 요청 분류(Coordinator)에는 가장 저렴하고 빠른 Haiku를, 계획 수립(Planner)에만 가장 똑똑한 Opus를 씁니다. 나머지 실행 역할은 Sonnet이 맡습니다. 역할마다 필요한 능력이 다르니 모델도 다르게 고르는 것입니다.

### 2. 실행 전에 계획을 확인받습니다

요리를 반쯤 만든 뒤에 "사실 매운 걸 못 먹어요"라는 말을 들으면 처음부터 다시 해야 합니다. 그래서 Deep Insight는 실행 전에 계획을 사람에게 보여 주고 승인을 받습니다. 원문은 이렇게 하면 중간에 방향이 바뀌어 앞선 작업이 버려지는 일이 줄어든다고 설명합니다.

### 3. 만든 사람과 검사하는 사람을 나눕니다

Validator는 Coder의 보고를 믿지 않습니다. Coder가 남긴 계산 기록을 보고 원본 데이터로 **직접 다시 계산**해서 비교합니다. 요리사가 "간 잘 맞아요"라고 말하는 것과 검수 담당이 직접 맛을 보는 것은 다릅니다.

### 4. 각자 자기 책상에서 일합니다 (컨텍스트 격리)

모든 에이전트가 하나의 대화를 공유하면 대화가 금방 꽉 찹니다. Deep Insight는 에이전트마다 **독립된 컨텍스트**를 주고, 다음 에이전트에게는 "다 했습니다"라는 신호와 짧은 요약만 넘깁니다. 원문에 따르면 가장 많은 내용을 다루는 Coder도 컨텍스트가 약 25K 토큰을 넘지 않는다고 합니다. 이 부분은 다음 글에서 자세히 다룹니다.

### 5. 반복해서 부르는 역할에만 캐시를 켭니다

프롬프트 캐싱은 같은 앞부분을 반복해서 보낼 때 비용을 줄여 주는 기능입니다. Deep Insight는 여러 번 호출되고 프롬프트가 긴 역할에만 캐싱을 적용합니다. 매번 내용이 달라지는 역할에 켜면 이득이 없기 때문입니다.

## 왜 1인 개발 환경에도 맞는가

Deep Insight는 데이터 분석 시스템이지만, 역할 구조는 소프트웨어 개발과 잘 맞습니다. 제가 겪던 문제와 나란히 놓아 보면 이렇습니다.

| 내가 겪던 문제 | Deep Insight의 해법 | 개발 작업에서는 |
|---|---|---|
| 대화 하나가 금방 꽉 참 | 에이전트별 독립 컨텍스트, 요약만 전달 | 작업마다 별도 세션과 작업 폴더를 주고, 결과는 짧은 보고로 받음 |
| 고친 세션이 스스로 "통과"라고 보고 | Validator가 다시 계산 | 다른 에이전트가 테스트와 점검을 다시 돌림 |
| 배포 전에 확인을 빼먹음 | Plan Reviewer(사람 승인) | 위험한 작업은 계획을 승인받은 뒤에만 실행 |
| 어디까지 했는지 헷갈림 | 체크리스트(`full_plan`)와 Tracker | 계획 파일의 체크박스와 상태 문서를 갱신 |
| 간단한 질문에도 무거운 절차 | Coordinator가 간단한 요청은 직접 처리 | 작은 작업은 계획 없이 바로 처리 |

마지막 줄이 생각보다 중요합니다. 모든 요청에 계획과 승인 절차를 거치면 오히려 느려집니다. Coordinator가 "이건 바로 하면 되는 일"을 걸러 주는 덕분에 무거운 절차는 필요한 작업에만 쓰입니다.

## 정리

- Deep Insight는 **분류(Coordinator) → 계획(Planner) → 사람 승인(Plan Reviewer) → 지휘(Supervisor) → 실행(Coder, Validator, Reporter) → 진행 기록(Tracker)** 으로 역할을 나눕니다.
- 핵심은 역할마다 맞는 모델을 쓰는 것, 실행 전에 계획을 확인받는 것, 만든 사람과 검사하는 사람을 나누는 것, 에이전트마다 컨텍스트를 분리하는 것입니다.
- 이 구조는 혼자 AI 에이전트 여러 개와 개발할 때 생기는 문제(대화 포화, 자기 검증, 확인 누락)에 그대로 쓸 수 있습니다.
